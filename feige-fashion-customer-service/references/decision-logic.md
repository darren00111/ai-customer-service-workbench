## 一、输入输出

**输入**

| 参数 | 含义 | 来源 |
|---|---|---|
| `--text` | 顾客**最新一条**消息 | `read_conversation.py` 的 `latestBuyerMessage` |
| `--product` | **飞鸽会话上的商品卡**（product_id / 标题 / sku_code） | 飞鸽商品卡；没有就不传 |
| `--context` | **会话级商品槽位**：本会话上一轮已确认的商品 | 调用方维护，见第四节 |
| `--store` | 店铺 ID | 默认 `shop_001` |

**输出**（`--json` 给出结构化结果）

| 字段 | 含义 |
|---|---|
| `category` | 分类，见下表 |
| `action` | `reply` 可直接答 / `ask_followup` 追问 / `handoff` 转人工 |
| `reason` | 判定依据（人可读） |
| `product_id` / `product_title` | 命中商品 |
| `matched_by` | 商品是怎么定位到的：`card` / `text` / `context` / `ambiguous` / `card_miss` |
| `candidates` | 歧义时的候选商品列表（供顾客点选） |
| `missing` | 缺失项，如 `["height","weight"]` |
| `evidence` | 用到了哪几项资料 |
| `draft_reply` | 回复草稿 |
| `handoff_reason` | 转人工原因（通知人工时用） |
| `parsed` | 抽到的身高体重（仅尺码类） |

| `handoff_dispute` | handoff | 投诉/差评/赔偿/平台介入/律师 |
| `handoff_after_sale` | handoff | 退货/换货/退款/补发/少件，或商品已下架 |
| `handoff_quality` | handoff | 质量词 + **已然**语气 |
| `handoff_data_gap` | handoff | 商品侧资料缺失，不编；商品卡商品未入库 |
| `handoff_stock_out` | handoff | 全码无货，自动回复帮不上 |
| `handoff_bargain` | handoff | 议价让利，由人决定 |
| `handoff_unknown` | handoff | 兜底，认不出来 |
| `need_product` | ask_followup | 认不出是哪款商品（有候选则列候选） |
| `pre_sale_availability` | reply | 问「有没有卖 X」且已定位到商品 |
| `pre_sale_stock` | reply | 库存/颜色 |
| `pre_sale_price` | reply | 价格 |
| `pre_sale_promo` | reply | 店铺优惠。不需要商品 |
| `pre_sale_size` | reply / ask_followup | 尺码 |
| `pre_sale_fabric` | reply | 面料 |
| `pre_sale_fit` | reply | 版型 |
| `pre_sale_shipping` | reply | 发货/物流。不需要商品 |

| `pre_sale_greeting` | reply | **寒暄**（你好 / 在吗）。不需要商品 |

**不需要商品就能答的分类**（顾客不点商品卡也照常回）：
`pre_sale_policy`、`pre_sale_shipping`、`pre_sale_promo`，以及全部 `handoff_*`。

## 三、优先级链（**先命中先返回，顺序即优先级**）

```
R1   明确要人工 ───────────────► handoff
R2a  具名政策咨询 ─────────────► reply        ← 必须排在售后之前
R2   售后 / 质量 / 纠纷 ────────► handoff
R2b  议价 ───────────────────► handoff      ← 必须排在「商品定位」之前
R0   跨款横向比较 ─────────────► reply        ← 必须排在 ambiguous 之前
     「认不出商品」的统一出口 ───► ask_followup（有候选则列候选）
R3   库存 / 颜色 ──────────────► reply（全码无货 / 已下架 → handoff）
R3.5 价格 / 优惠 ──────────────► reply
R4   尺码 ────────────────────► reply / ask_followup
R4.5 有无此商品 ─────────────► reply        ← 必须排在尺码 / 库存之后
R5   面料（含性能承诺类）────────► reply / handoff
R6   版型 ────────────────────► reply / handoff
R7   发货 ────────────────────► reply
R1g  寒暄 ────────────────────► reply        ← 放最后，避免吞掉真诉求
R8   兜底 ────────────────────► handoff
```

**为什么售后必须排在售前前面**：顾客说「我要退货，尺码不合适」同时命中「退货」和「尺码」。
若售前优先，就会去推荐尺码——这是事故。

**为什么 R4.5 必须排在尺码 / 库存之后**：它的触发词里有「有没有」，
若不后置，「有没有 M 码」「有货吗」会被它吞掉，答非所问。

**为什么政策要排在售后前面**：「支持七天无理由吗」是纯政策咨询，该答；
但它含「无理由」，若不前置，会被售后类的保守逻辑吞掉直接转人工。
放行条件很窄：**只认具名政策短语，且句子里没有第一人称行动词**
（「我要用七天无理由退货」有「我要」→ 仍是售后 → 转人工）。

**为什么 R2b 议价要排在商品定位之前**：「你们家那个裤子还能便宜吗」同时命中
两款裤子，若让「认不出商品」先处理，就会变成「请点选商品」；顾客选完款照样
得转人工——白绕一圈，还让顾客以为有得谈。议价涉及让利，**无论指哪款都必须
转人工**，这个判断与商品无关。

**为什么 R0 比较要排在 ambiguous 之前**：见 5.3。

**为什么 R1g 寒暄要放最后**：见 5.4。

## 四、商品定位：三级优先链

顾客**不点商品卡**是常态。定位不到商品，一切商品级问题都塌了。所以商品定位是独立一层：

```
P1  飞鸽商品卡         最可靠。顾客从商品详情页点「客服」进来时飞鸽自动带上，
                       完全不依赖顾客措辞。没标定前这一级是空的。
P2  消息文本           顾客自己说了商品名或特征：「碎花的裙子」「阔腿裤」「针织开衫」。
P3  会话级商品槽位     本会话上一轮已确认的商品。顾客说「这个」「它」时继承它。
```

**文本匹配怎么做的**（`kb.py`）：

1. 拿商品标题与消息做最长公共子串打分。
2. 标题里的通用词先剔掉（`女装`/`春秋`/`长袖`…），避免「每件都含女」导致全命中。
3. **纯由泛字组成的匹配作废**：`裤`/`裙`/`衣` 这类单字太泛，一家店可能同时有 5 条裤子。
4. **品类一致性过滤**：消息里有「裤」，就不可能是在问「裙」——
   否则「高腰裤有M码吗」会把「高腰A字半身裙」也列成候选。
5. 最高分**并列**时**不猜**，全部作为候选交给顾客点选。

**歧义不是死胡同。** 早期版本歧义时只会说「麻烦告诉我您想咨询的是哪一款商品」——
让顾客重述一遍，转化率很差。现在的回复是列候选：

```
亲，您问的应该是下面这几款里的哪一款呢？
1. 高腰直筒水洗牛仔长裤
2. 高腰拖地阔腿西装裤
回复序号或名字都可以，我马上帮您查～
```

顾客回「2」，槽位就写入 P1009，后续所有指代都继承它。

**槽位更新规则**（调用方维护，`demo_nocard_session.py` 是参考实现）：

| 本轮结果 | 槽位动作 |
|---|---|
| 唯一命中商品（`product_id` 有值） | 写入该商品 |
| 给出候选、顾客回序号 | 按序号写入 |
| `handoff` / 认不出来 | **不动**（不强改，避免污染） |

**还有一种情况要单独说**：飞鸽商品卡指向的商品**不在知识库里**（新上架还没入库）。
这和「不知道问哪款」是两回事——不能反问顾客，只能转人工。
判为 `card_miss` → `handoff_data_gap`，`handoff_reason = 商品卡商品未入库`。

## 五、四个容易做错的地方

### 5.1 同一个词，疑问是售前，已然是售后

「起球」这个词本身没有立场，**语境决定分类**：

| 顾客说 | 判定 | 结果 |
|---|---|---|
| 会不会起球 | 疑问（`吗/会不会/是否/?`） | 售前面料咨询 → 但属性能承诺类，资料没写 → **转人工** |
| 起球吗 | 疑问 | 同上 |
| 才穿两天就起球了 | 已然（`了/已经/才穿/刚收到`） | **质量问题 → 转人工** |

规则：**疑问标记优先于已然标记**。即只要句子里有疑问词，就判为「在问」。
（否则「起球了吗」会被「了」误判成抱怨。）

### 5.2 缺失分两种，处理方式完全不同

| 缺什么 | 例子 | 动作 |
|---|---|---|
| **顾客侧**信息 | 问尺码但没说身高体重 | `ask_followup` —— 追问顾客 |
| **商品侧**资料 | 问洗护，但资料里 `material.care` 是空的 | `handoff` —— 转人工，**绝不编** |

把这两者混为一谈，要么该追问的去骚扰人工，要么该转人工的瞎编答案。

### 5.3 「哪个最好」是在要结论，不是没说是哪款

顾客说「你们现在哪个裤子材质是最好的」，同时命中了两款裤子。
早期实现把它判成 `ambiguous` → 「请点选商品」——**误判**：他不是没说是哪款，
他是明知有多款、故意要横向比。他要的是结论，不是选项列表。

**但回复里绝不能排序。** 两个原因，都不是洁癖：

1. 绝对化用语在广告法上是明确红线（「最佳」「第一」同档）；
2. 我们只有成分 / 克重这类客观数据，对顾客的手感偏好没有判断依据——
   本来就没资格说哪款「最好」。

正确姿势是**按维度把客观差异摊开 + 给出「在意什么就选什么」的映射 + 问侧重**：

```
亲，这几款在面料上确实不一样，没法一概而论，主要看您更在意什么：
· 高腰直筒水洗牛仔长裤 —— 棉 98%、氨纶 2%，克重约 320g/㎡，微弹，厚薄属常规
· 高腰拖地阔腿西装裤 —— 粘胶 70%、聚酯纤维 25%、氨纶 5%，克重约 290g/㎡，微弹，厚薄属常规

想更挺括耐穿，就选成分里棉占比高的那款；想更垂顺轻凉，就看粘胶/聚酯占比高的那款。
您更看重哪一点？我按您的侧重帮您定款～
```

注意「想更挺括耐穿就选棉占比高的那款」是把**客观属性映射到需求**，
不是评价哪款更好——这个区别决定了它能不能发出去。

**触发条件的两道护栏**（都对应实测踩过的坑）：

| 护栏 | 反例 | 为什么不能算比较 |
|---|---|---|
| 裸「哪个」不算比较词 | 哪个颜色有货 / 哪个码最合适 | 「哪个」修饰的是**属性**，不是商品 |
| 明确问尺码的不算 | 哪个码最合适 | 单款尺码问题，不是横向比 |

只有带商品量词的（哪款 / 哪条 / 哪件 / 哪种）或「哪X + 品类词」才是跨款比较。
「哪条裤子尺码全」算，「哪个码最合适」不算。

**圈不出品类就退回追问。** 「哪款面料更舒服」不含任何品类词，圈不出比较范围——
这时宁可退回「请告诉我您想咨询哪款」，也不要全店 10 件乱比一遍。

代码位置：`classify.py` 的 `is_compare()` / `_which_kind()` / `_compare_pool()` / `reply_compare()`。

### 5.4 打招呼不能转人工

「你好」「在吗」被判成 `handoff_unknown`（意图不明 → 转人工）是**灾难级**错误：
顾客只是打个招呼，却等来一句「帮您转接人工」，会觉得店里根本没人。

现在走 `pre_sale_greeting` → 回「在的」+ 给几个开口方向。

**但寒暄分支必须放在所有强规则之后**，因为：

| 顾客说 | 必须判成 | 若寒暄优先会怎样 |
|---|---|---|
| 你好，这个能便宜吗 | 议价 → 转人工 | 只回一句问候，把议价诉求丢掉 |
| 你好我要退货 | 售后 → 转人工 | 只回一句问候，把退货诉求丢掉 |

这两条都是实际会挨投诉的误判，所以寒暄只能做「所有规则都不命中」时的兜底。

**「整条都是寒暄」这个约束是关键**：消息去标点后长度 ≤ 14 且能匹配寒暄词，
才算纯寒暄。「在吗这个有M码吗」带诉求 → 不是寒暄。

**喊人 vs 寒暄要分开**：

| 说法 | 判为 | 理由 |
|---|---|---|
| 你好 / 在吗 / 在不在 / 客服在吗 | 寒暄 → 回「在的」 | 找人应答，回一句就是最优解 |
| 人呢 / 客服呢 / 怎么没人 | 要人工 → 转人工 | 带**催促 / 不耐**，顾客已经在等 |

转人工在这里是负体验（多一次无谓介入，顾客还得多等），而`人呢`那种转人工是对的。
区分依据是**语气**，不是字面。

代码位置：`classify.py` 的 `GREET_WORDS` / `is_pure_greeting()` / `reply_greeting()`。

## 六、尺码推荐

### 算法

1. 从消息里抽身高体重（先认「身高160」「体重50公斤」这类带前缀的，再认带单位的，最后用裸数字兜底）。
   - 区间不重叠是关键：身高取 140–210，体重取 35–130。
   - **「斤」必须先判**，否则「100 斤」会被当成 100 公斤。
2. 用 `store.yaml` 的 `size_guide.table` 做**中心点距离匹配**：
   `距离 = |身高差| × 1.0 + |体重差| × 1.0`，取最小。
3. 若最优与次优距离差 < 3，判为**临界码**，回复里必须提示「另一个码也接近」。承认不确定性比假装精确更诚实。
4. 把推荐码**对齐到商品实际尺码**：
   - 商品有该码 → 直接用；
   - 商品是 S/M/L/XL 体系但没该码 → 取最接近并说明；
   - 商品是数字码体系（如牛仔裤 26–30）→ **不硬套**，改为让顾客对照腰围。

### 措辞红线

- 必须用「**更建议**」「可以参考」。
- 禁止「保证合身」「百分百」「绝对」「一定能」。
- 必须说明尺码表**口径**：成衣尺寸 / 净尺寸，二者差别很大，不写就是误导。
- `test_classify.py` 里有自动化断言，出现禁用词直接判失败。

## 七、回复口径

| 场景 | 口径 |
|---|---|
| 一般转人工 | 「需要人工客服结合订单情况核实，我已经为您转接」 |
| 资料缺失/意图不明/全码缺货/议价 | 「这个我帮您转接人工客服确认一下，请稍等～」 |
| 追问身高体重 | 「麻烦告诉我一下您的身高和体重（例如 160cm / 50kg）」 |
| 认不出商品、无候选 | 「麻烦告诉我您想咨询的是哪一款商品」 |
| 认不出商品、有候选 | 列候选 + 「回复序号或名字都可以，我马上帮您查～」 |

占位回复**不得**承诺处理结果、到账时间或赔偿金额。

## 十、已知边界

- **商品匹配靠标题公共子串**，商品上千时精度必然下降。歧义只是不猜，
  但真正的解法是**接上飞鸽商品卡**（P1 级），文本匹配只作兜底。
- **`size_guide` 是示例值**，必须商家核准后替换，否则尺码建议不可信。
- **商品资料也是构造数据**（`sample_data: true`），换真实资料前回复不能对外用。
- **槽位由调用方维护**，`classify.py` 只接收不存储。多轮状态由
  `watch_feige.py` / `reply_once.py` 落盘到 `data/state.json`。
- **抽身高体重的裸数字兜底有误判风险**，比如消息里出现无关数字。
- **跨款比较只支持品类内 2~5 款**（`kb.MAX_CANDIDATES`）。超过 5 款不比较，
  退回追问——一次列十几款对顾客是负担，不是服务。
- **`pre_sale_compare` 的「怎么选」映射是硬编码在 `DIM_GUIDE` 里的通用话术**，
  按维度写，不针对具体商品。换品类（比如卖家电）需要重写这一节。
