# 无商品卡咨询：处理逻辑与测试手册

> 场景：**顾客不点商品卡，直接打字问**。
> 这是常态，不是异常——顾客从店铺主页、订单页、老客回购进来时都没有商品卡。
> 配套代码：`scripts/watch_feige.py`（监听判定）、`scripts/classify.py`（决策）、`scripts/kb.py`（商品定位）。

## 一、什么叫「无商品卡」

飞鸽左侧「咨询商品」面板为空（显示「暂无咨询商品」）。此时系统只知道**有人说话**，
不知道**在说哪件商品**——所有商品级问题（尺码/库存/面料/价格）都失去答案来源。

判断方式（`watch_feige.py` 自动做）：读左侧面板，命中占位词即视为无卡。
注意左侧面板会混入订单、拉黑等无关文本，所以**命中不了知识库就降级为无卡重跑**，
不让噪音把判定拖进「商品未入库」的死路。

## 二、四个环节与预期表现

| 环节 | 做什么 | 预期表现 | 失败信号 |
|---|---|---|---|
| ① 进入后台 | 起带调试端口的可见 Chrome → 打开飞鸽工作台 | 窗口标题「飞鸽客服系统」，端口 9222 通 | 无窗口（默认无头）、`MainWindowHandle=0` |
| ② 选中会话 | 点「最近联系」→ 点买家 | 读到气泡数 > 0，输入框就绪 | 气泡 0、提示「组件渲染中」 |
| ③ 接收消息 | 轮询读页面，比对买家消息指纹 | 有新消息才触发判定，无新消息静默 | 同一条被反复判定 = 指纹设计有问题 |
| ④ 识别与响应 | 定位商品 → 走优先级链 → 出分类与草稿 | 见下表 | 分类跳变、草稿自相矛盾 |

### 环节 ①②的既有坑

- `agent-browser open` 默认**无头**，`--headed` 在本机不生效 → 必须自己起 Chrome 带 `--remote-debugging-port=9222`，再统一用 `--cdp 9222` 接管。
- 「当前会话」页签可能是空的，真人都在「最近联系」。
- 打开工作台后要等组件渲染完再读，否则读到「组件渲染中，请稍后...」。

### 环节 ③的指纹设计（关键）

用 **买家消息条数 + 最新买家消息** 做指纹，**不用最后一条消息**。
原因：系统提示（超时提醒、接入通知）会不断冒出来，用最后一条消息做指纹，
会明明没有新咨询却判定成有新消息。

指纹还要**按会话隔离**。实测中页面一度切到另一个买家，切回来后同一条消息被判了 3 次——
重复追问、重复通知是实际事故。状态文件 `data/state.json` 现在是 `conversations: {买家: {...}}` 结构。

## 三、没有商品卡时，商品怎么定位

```
P1  飞鸽商品卡     无卡场景下这一级是空的（本场景的前提）
P2  消息文本        顾客自己说了商品名/特征：「阔腿裤」「碎花的裙子」
                    + 纯品类兜底：只说品类（「裙子呢」「有卖羽绒服吗」）也能命中
P3  会话级商品槽位  本会话上轮已确认的商品，顾客说「这个」「它」时继承
```

P2 的两个过滤器，都是实测踩出来的：

- **泛字作废**：匹配子串若只由「裤裙衣装款个这那件套的」构成，视为没匹配。否则一家店里 5 条裤子全成候选。
- **品类一致性**：顾客说「裤」就不可能问「裙」。否则「高腰裤有M码吗」会把「高腰A字半身裙」列进来。
- **纯品类兜底**：「裙子呢」跟任何标题的公共子串都只有「裙」这个泛字，会被上面那条判废。
  所以子串全废时再走一次品类兜底，把该品类的商品列出来给顾客点。

## 四、预期表现（实测，2026-09-22）

顾客全程不发商品卡，知识库 10 件商品：

| 顾客说 | 分类 | 动作 | 说明 |
|---|---|---|---|
| 阔腿裤160 50公斤买什么码 | pre_sale_size | ✅回复 | P2 文本定位成功，给出 M 码 + 口径说明 |
| 你们家有卖羽绒服吗 | pre_sale_availability | ✅回复 | 品类兜底命中唯一商品 |
| 发什么快递 | pre_sale_shipping | ✅回复 | 店铺级，根本不需要商品 |
| 支持七天无理由吗 | pre_sale_policy | ✅回复 | 同上 |
| 裙子呢 | need_product | ❓列候选 | 店里 2 款裙子，列出来让顾客点 |
| 高腰裤有M码吗 | need_product | ❓列候选 | 2 款高腰裤冲突，不猜 |
| 这个有M码吗 | need_product | ❓追问 | 纯指代且无槽位，只能问 |
| 能机洗吗 | need_product | ❓追问 | 先定商品，再谈洗护 |
| 我要退货 | handoff_after_sale | 🔔转人工 | 售后不需要商品 |
| 才穿两天就起球了 | handoff_quality | 🔔转人工 | 已然语气 |
| 那个裤子还能便宜吗 | handoff_bargain | 🔔转人工 | 议价由人决定 |
| 人呢 | handoff_human_request | 🔔转人工 | 喊人 = 要人工，不是「意图不明」 |
| 亲在吗 / 😊 | handoff_unknown | 🔔转人工 | 兜底 |

**结论：无卡场景不是不能答，是能答的比例取决于顾客说没说商品特征。**
顾客给出品类或特征 → 能答；只说「这个」→ 追问；涉及让利/售后 → 转人工（与有无商品卡无关）。

## 五、测试时重点盯的边界

### 5.1 会误判的地方

| 边界 | 现象 | 当前处理 |
|---|---|---|
| 顾客回序号「2」 | 上一轮列了候选 | 槽位落定为该候选，后续继承 |
| 顾客发相同内容两次 | 指纹靠条数区分 | 不漏（条数变了） |
| 跨商品比较「哪个材质最好」 | 判定为歧义列候选 | **偏保守但不理想**——它其实是要推荐，不是要选商品 |
| 纯表情 / 单字 | 转人工 | 可接受，但真实场景里可能显得冷淡 |
| 消息里带无关数字 | 可能被当身高体重 | 已知风险，未做上下文校验 |

### 5.2 常见异常与处置

| 异常 | 表现 | 处置 |
|---|---|---|
| 会话漂移 | 读到的买家突然变了 | 状态已按会话隔离；日志会打印「会话已切换」 |
| 重复判定 | 同一条消息多次 NEW | 已由会话隔离修复 |
| 页面渲染未完成 | 气泡 0 / 「组件渲染中」 | 等待后重读；不要当作会话为空 |
| 登录过期 | 提示重新登录 | 必须人工扫码，不绕 |
| 平台智能客服抢答 | 抖音自带机器人先回了 | **真实存在**：实测它先答了「价格以页面为准」。两套答复会打架，上线前必须二选一 |
| 商品卡有但不在知识库 | `card_miss` | 降级为无卡重跑，而不是直接转人工 |

## 六、怎么跑

```bash
# 1. 开浏览器（可见 + 调试端口）
scripts\start_feige_browser.bat

# 2. 生成读取载荷
python scripts/read_conversation.py --emit-payload payload.txt

# 3. 轮询：读一次 → 判一次（只在有新买家消息时输出判定）
agent-browser --cdp 9222 --max-output 200000 eval "$(< payload.txt)" > raw.json
python scripts/watch_feige.py --from-raw raw.json --state data/state.json

# 强制判定当前这条（不管是不是新消息）
python scripts/watch_feige.py --from-raw raw.json --state data/state.json --force
```

`watch_feige.py` **只读、只出建议，绝不写入输入框、绝不点发送**。
这三件事写在文件头，谁改都别破。

## 七、当前限制（必须知道）

- **知识库与真实店铺不匹配**：`shop_001` 里是 10 件女装，飞鸽真实店铺是台球用品。
  本轮测的是**决策逻辑对不对**，不是**答复内容对不对**。真实资料到位前，草稿不能对外发。
- **P1 商品卡未标定**：需要一个「有咨询商品」的会话。没有它，无卡场景只能靠文本猜。
- **不做多轮语义理解**：只按最新一条消息判定，靠槽位继承上下文。
