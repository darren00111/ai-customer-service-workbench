# 资料入库与目录约定

> 目标：**先让链路端到端跑通，暂不追求内容完善。**
> 因此这里定义的是「最小可用」的资料标准——够触发三类判断即可，之后再补全。

## 目录结构

```
feige-fashion-customer-service/
├── data/
│   ├── stores/
│   │   └── shop_001/                    # 一家店一个目录
│   │       ├── store.yaml               # 店铺级配置
│   │       ├── products/
│   │       │   ├── p_1001.yaml          # 一个商品一个文件
│   │       │   └── p_1002.yaml
│   │       └── raw/                     # 你上传的原始资料（图片/表格/文档）
│   │           ├── size-chart-1001.png
│   │           └── fabric-spec.docx
│   └── conversations/                   # 对话记录（阶段 4 启用）
│       └── 2026-09-22.jsonl
└── scripts/
```

**原则**：
- `raw/` 放**原始文件**，原样保留，不改不删——可追溯
- `*.yaml` 是**结构化的可读资料**，由原始资料整理而来
- 原始资料优先：整理时若与 `raw/` 冲突，以 `raw/` 为准并标注

## 阶段 2 的最小资料标准

为了让管线跑通，每个商品**只需要这几个字段**：

| 字段 | 为什么必须 | 示例 |
|---|---|---|
| `title` | 用来对上是哪个商品 | 高腰阔腿裤 |
| `category` | 影响尺码建议口径（决定「裙长/裤长/衣长」） | 裤装 |
| `variants` | 颜色 × 尺码库存，判断有没有 M 码 | 见下 |
| `size_chart` | 尺码咨询必用 | 见下 |
| `material` | 面料咨询必用 | 聚酯纤维 95% 氨纶 5% |
| `fit` | 版型建议必用 | 修身 / 宽松 |

实际落地格式（可直接照抄，参考 `data/stores/shop_001/products/p1009.yaml`）：

```yaml
product_id: P1009
title: 高腰拖地阔腿西装裤
category: 裤装
status: on_sale            # on_sale / sold_out / pre_sale / off_shelf

size_chart:
  basis: 净尺寸             # ⚠️ 成衣尺寸 或 净尺寸，二选一，必须写明
  unit: cm
  rows:
    - {size: S,  waist: 64, hip: 92,  length: 102}
    - {size: M,  waist: 68, hip: 96,  length: 103}
    - {size: L,  waist: 72, hip: 100, length: 104}
    # 该商品没有的字段填 null，不要省略

material:
  composition:
    - {fiber: 粘胶,     percent: 70}
    - {fiber: 聚酯纤维, percent: 25}
    - {fiber: 氨纶,     percent: 5}
  lining: null
  weight_gsm: 290
  elasticity: 微弹
  thickness: 常规
  care: null               # 洗护；留空则「问洗护」会转人工，不会瞎编

fit:
  silhouette: 阔腿
  waistline: 高腰
  fit_type: 宽松
  notes: 拖地裤长，前褶设计，建议按身高选码

# 颜色 × 尺码库存矩阵。0 表示该组合售罄。
# 决策逻辑靠它回答「有没有 M 码」「有没有黑色」
variants:
  - color: 黑
    sizes: {S: 22, M: 34, L: 28, XL: 16}
  - color: 米白
    sizes: {S: 18, M: 26, L: 0,  XL: 24}
```

**两个最容易出错的地方**：

1. **口径不写清楚，尺码建议就是错的**——成衣尺寸和净尺寸差一个活动余量，
   顾客按错的对照就会买错。文件里漏了 `basis`，`classify.py` 会照常推荐，
   但回复里说不出口径，等于埋雷。
2. **库存给到 SKU 级，不要只给商品级**——只写「库存 168」，
   「有没有 M 码」就没法答。`variants` 要细到颜色 × 尺码。

## 你可以怎么提供资料

按顺序，哪一步方便就从哪开始：

### 方式 A：直接上传原始文件（推荐先做）

把商品资料丢进对话，或放进 `data/stores/shop_001/raw/`。可以是：
- 尺码表截图 / Excel
- 商品详情页截图
- 面料成分文档
- 已有的话术表格

**不用整理**，原始状态就行。我来负责转成结构化 yaml。

### 方式 B：口述最小字段

懒得上文件也可以，直接文字告诉我：
```
商品：高腰阔腿裤
颜色尺码：黑 S/M/L，卡其 M/L
面料：聚酯纤维95% 氨纶5%
版型：宽松
尺码：腰围 M 68cm，臀围 96cm，裤长 100cm（成衣尺寸）
```

### 方式 C：先给我店铺级信息

店铺级信息**不依赖商品**，是「顾客不点商品卡」时的主力可答项，性价比最高：

```yaml
store_id: shop_001
store_name: 示例女装店
shipping:
  lead_time: 48小时内发货
  carriers: [中通快递, 圆通速递]
  free_shipping_note: 满 99 元包邮
policies:                       # 具名政策：问到时直接答，不用商品
  return_policy: 支持七天无理由退换，商品需保持吊牌完好、未洗涤未穿着。
  invoice: 支持开具电子发票。
  authenticity: 官方直营，正品保证。
promotions:                     # 公开的店铺级活动（议价不在这里，议价一律转人工）
  note: 满 199 元减 20 元
handoff_message: 已为您转接人工客服
```

## 为什么「顾客不一定点商品卡」这件事会影响资料准备

真实客服里，顾客**直接打字问**是常态：从店铺主页进来、从订单进来、
老客户回购，这些会话里飞鸽的商品卡片都是空的。

系统找商品靠三级链：**飞鸽商品卡 > 消息文本 > 会话级商品槽位**。
资料准备时对应的三件事：

| 级别 | 你要做什么 | 不做会怎样 |
|---|---|---|
| 商品卡 | 无（系统层面标定） | 顾客从商品页进来时本可免问，白丢一次机会 |
| 消息文本 | **商品标题写得有区分度** | 标题都叫「时尚百搭女装」，顾客说「那条裤子」谁也定位不到 |
| 会话槽位 | 无（系统层面维护） | 顾客说「这个」时接不上话 |

**所以标题别写成同质化的营销词。** 「高腰直筒水洗牛仔长裤」比「时尚显瘦百搭女裤」
好得多——顾客说「牛仔的」「直筒的」都能定位到。

## 建议的推进顺序

```
1. 先给「店铺级信息」          → 我建 data/stores/shop_001/store.yaml
2. 再给 1 个商品的完整最小字段  → 我能跑通「读懂商品 → 生成尺码回答」单点
3. 补到 2~3 个商品             → 能验证多商品切换不串资料
4. 阶段 1 的飞鸽标定完成后      → 串起「读消息 → 查资料 → 出回复」全链路
```

**关键：第 1、2 步做完，管线的主要部分就能验证了。** 不需要等资料齐。

## 上传资料时的注意事项

- **可以脱敏**：店名、商品名、价格都可替换，不影响链路验证
- **不要放真实客户信息**：手机号、地址、订单号、聊天记录截图里的敏感信息
- **尺码表务必标口径**：成衣尺寸 vs 净尺寸，差别很大
- **一个颜色一行 SKU**：避免「不同颜色属性不同」被写成统一结论
