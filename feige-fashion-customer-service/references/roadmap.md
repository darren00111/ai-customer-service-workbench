# 项目框架与实施路线

> 本文档是 `feige-fashion-customer-service` 的总体设计与进度看板。
> 每次推进后更新「进度看板」；设计变更时更新「架构」。

## 一、这个 Skill 是什么

在**商家已登录的飞鸽网页版**（抖店商家 IM）中，充当服装店客服：
自动回答售前咨询，遇到售后/纠纷/不确定情况**立即停手并通知人工**。

**它不是**：一个能自己决定退款的客服、一个跨店复用的通用机器人、一个无人值守的全自动系统。
**它是**：一个「只会答资料里明确写过的售前问题、其余一律转人工」的保守型助手。

### 设计立场（贯穿全局）

| 立场 | 含义 |
|---|---|
| 保守优先 | 宁可转人工，不可乱答。答错的代价 > 多转一次的代价 |
| 资料驱动 | 没有审核过的资料，就不存在这个答案 |
| 店铺隔离 | 绝不跨店复用价格/库存/承诺 |
| 人工兜底 | 售后永不自动处理，只通知 |
| 可追溯 | 每个动作留记录（脱敏） |

**关键认知的更新**：主链路（读 → 判 → 发）已**端到端打通**（2026-09-22 实测）。
**现在最该补的是 L1 的商品卡标定**——它是**自动答复率的天花板**：

顾客不点商品卡也能进线（直接打字问「有 M 码吗」）。这类会话里，
商品卡是**唯一可靠**的商品来源；没有它，只能靠顾客措辞去猜，
猜不到就得列候选让顾客点。列候选能用，但点击率远不如直接答。

所以商品卡不是「锦上添花」，是自动答复率的**上限**。

## 三、数据流

```
顾客发消息
   ↓
[L1 感知 🟢] read_conversation.py
     读取：会话 / 消息 / 角色判定 / 最新买家消息
     🔴 商品卡、SKU、订单状态 —— 未标定
   ↓
[L2 决策 🟢] classify.py
     分类 → ①可答售前  ②顾客侧信息缺失  ③必须转人工
   ↓
   ├─① reply ─────► 查 [L3 知识库] → 生成回复草稿
   │                                → [L3 发送 🟢] 写入 → 校验 React 状态 → 提交 → 留痕
   │
   ├─② ask_followup ─► 追问一个关键信息（身高体重 / 哪款商品）→ 同样走发送
   │
   └─③ handoff ───► 占位回复**默认不发**（转人工入口未标定，不能承诺「已转接」）
   │                                            ↓
   │                                  [L4 通知 🟢] 脱敏 → 企微/微信
   ↓
[L3 记录 🟡] sent_log.jsonl 已记发送指纹；会话级分类/动作记录（🔴 待补）
```

## 五、当前阶段目标

**阶段性目标：先让整条处理链路端到端跑通并保持流畅，暂不追求知识库内容完善。**

这句话决定了优先级：

| 优先 | 次之 |
|---|---|
| 链路能通（读得到 → 判得对 → 发得出） | 知识库覆盖多少商品 |
| 每一步稳定可复现 | 回答的丰富度与话术打磨 |
| 小样本验证（1 店 + 2~3 商品即可） | 全量商品导入 |

**因此不再按"先建知识库再开发"的直觉顺序推进。** 正确顺序是：
先用**最小知识样本**（够触发三类判断即可）把管线打通，
链路验证稳定后，再回头把知识库内容补全——那时补内容只是填数据，不动代码。
