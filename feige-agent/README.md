## 与 Skill 的关系

| | Skill（feige-fashion-customer-service） | 本应用（feige-agent） |
|---|---|---|
| 定位 | 给 AI 读的说明书，需要有个大脑在环 | 可独立运行的程序，自己监听自己回复 |
| 判定规则 | `scripts/classify.py`（旧版女装规则） | 旧店铺复用旧规则；新店铺使用配置驱动的 `classify_standard.py` |
| 页面逻辑 | `scripts/feige_read.js` / `feige_send.js` | `app/assets/fga.js`（常驻注入版） |

每种配置格式各有一个决策入口：旧版 `store.yaml` 对应原规则，新版 `merchant.yaml` 对应通用规则。

## 为什么不用 agent-browser 了

旧方案每次操作都要起一个子进程，重复付出「进程启动 + Node 初始化 + CDP 握手」的成本。
本应用保持**一条常驻 CDP 长连接**，之后每次调用只是一次纯协议往返。

历史页面读写测量（同一台机器，不含本版千问推理时间）：

| 环节 | 旧方案（每命令起进程） | 本应用（常驻连接） |
|---|---|---|
| 读取会话 | 约 130 ms | **2.4 ms** |
| 写入 + 提交 | 约 260 ms | **2.7 ms** |
| 完整一轮（读 + 判 + 发） | 约 390 ms | **4.9 ms** |

## 运行

```bash
# 打开桌面控制台
python run.py desktop

# 环境自检
python run.py doctor

# 拉起浏览器并连接（首次会提示扫码登录飞鸽）
python run.py boot

# 看当前会话
python run.py peek

# 跑一轮（判定 + 发送）
python run.py once

# 只判定，不发送
python run.py once --dry

# 连续监听
python run.py watch --seconds 60

# 生成 10 店隔离配置（首次执行一次）
python run.py multi-init --count 10

# 检查多店端口、profile 和知识库映射
python run.py multi-doctor

# 启动全部店铺；最多同时拉起 3 个浏览器，避免启动瞬间占满机器
python run.py multi-boot --parallel 3 --seconds 3600
```

Windows 上也可以直接双击 `启动飞鸽客服.bat`，不会额外保留命令行窗口。

已经打包的 Windows 程序位于 `dist/FeigeCustomerService/FeigeCustomerService.exe`。
必须保留整个 `FeigeCustomerService` 文件夹；外部的 `data` 和 `knowledge` 目录分别保存
店铺配置、运行数据和可编辑商品知识库。重新打包可运行 `build_desktop.ps1`。

桌面控制台只保留日常需要的功能：查看十店状态、启动全部店铺、单店启停、查看回复统计，
以及集中处理退换货、质量、投诉和人工请求。端口、profile 路径和知识库映射仍由
`data/stores.json` 管理，不占用日常操作界面。

首次需要 Chrome 或 Edge。应用会用自己的 profile 目录启动浏览器并打开飞鸽后台，
登录一次后长期有效（cookie 持久化在 `data/chrome-profile`）。

## 多店架构

`data/stores.json` 是桌面端未来直接读写的店铺注册表。每个店铺必须拥有独立的：

- CDP 调试端口；
- 浏览器 profile 和登录态；
- 知识库映射；
- 会话指纹、暂停状态和限速窗口；
- 运行日志。

`MultiStoreSupervisor` 为每个店铺创建一套 `FeigeAgent`，负责限流并发启动、聚合状态、
监听线程自动拉起、浏览器崩溃后重启和 CDP 重连。桌面界面只需调用它的
`boot_all()`、`boot_store()`、`stop_store()`、`status()` 和 `shutdown()`，无需再复制一套引擎。

所有退换货、质量、投诉和人工请求统一写入 `data/notifications.jsonl`。十个店铺不会
各自争抢个人微信窗口；桌面端后续只需用一个串行通知进程消费该队列，再接已经验证过的
个人微信投递。切换企业微信时也不需要修改客服引擎。

监听每轮会扫描侧栏多个会话，未读优先。会话列表发生排序变化时会重新定位，最终再由
“店铺独立状态文件 + 会话 key + 平台消息 ID（可用时）+ 发送前原子占用”四层去重。
1.0 的旧指纹仍可识别，升级不会把旧消息误当成新消息。指纹只统计买家消息，客服自己
发出的气泡不会再次触发旧问题；当前最后一条不是买家消息时也禁止发送。

同一店铺的后台扫描、立即检查、人工草稿发送和状态探测共用一把页面控制锁，完整操作
结束前其他操作不会插入点击或切换会话。发送后必须看到内容一致的客服气泡才记为成功；
如果已经点击但无法确认结果，系统会保留占用并停止自动重试，交由人工核对，避免重复发送。

1.1.1 修复新浏览器 profile 启动时误绑定临时标签页的问题：连接会等待飞鸽目标页；已经进入

### 自动补问与人工草稿

- `need_product` 和资料不完整的尺码咨询允许自动补问，发送后等待新的买家消息。
- 售后、质量、投诉、议价、商品资料缺口和未知意图只生成上下文草稿，并锁定该会话。
- 控制台可编辑草稿并确认发送。发送前重新核对店铺、会话、买家、最新买家消息和最后消息角色。
- 人工发送期间暂停该店铺的后台扫描，避免页面被监听线程切走。
- 确认发送或标记已处理后记录原消息指纹、解除会话锁，下一条买家消息可以重新进入自动判断。
- 升级前已经排队的人工消息会按类别补齐安全草稿。

当前 `stores.json` 已生成 10 个槽位（端口 9222–9231）。`shop_001` 沿用已有浏览器
profile，其余店铺首次启动时各自打开登录窗口，需要分别完成一次登录。

## 自测

```bash
python tests/selftest_engine.py   # 通道 / 注入 / 读取 / 发送闸门 / 性能（22 项）
python tests/selftest_store.py    # 防重复 / 并发占用 / 暂停 / 限速（21 项）
python tests/selftest_multistore.py # 12 店并发 / 隔离 / 恢复 / 48 会话压测（18 项）
python tests/selftest_browser_fleet.py # 10 个真实 Chrome/CDP/profile 并发通道
python tests/selftest_notifications.py # 10 店并发写入与通知去重（4 项）
python tests/selftest_desktop.py      # 桌面 API 与基础可访问性（8 项）
python tests/selftest_ui_browser.py   # 1240/700/320 px 真浏览器交互（5 项）
```

引擎自测跑在本地模拟页上，**不需要登录飞鸽**——这样把「代码对不对」和
「真实环境能不能登录」拆成两件事，改代码时不必每次都去碰真实后台。

## 三层安全兜底

按「全部自动发送」的配置，以下机制仍在生效：

1. **发送闸门**：写入后校验 React 状态（用输入框的 `N/800` 字数计数当同步指示灯），
   没同步就拒绝发送；提交前确认输入框非空——防止给客户发空消息。
2. **速率限制**：单店铺每分钟发送上限（默认 20 条），超出排队而不是硬发。
3. **随机停顿**：每次发送前随机等待 0.8–2.2 秒，避免节奏过于规律被平台判定为机器人。

4. **结果确认**：发送后等待对应客服气泡出现；结果不明时不自动重发。

另外，转人工的会话会自动暂停自动回复，不会出现「一边说转人工一边继续自动答」。

## 前提依赖

**这套方案依赖浏览器，不是平台 API。** 原因是飞鸽的网页接口没有对卖家开放。
因此应用必须自己承担「把浏览器拉起来并确认登录」的职责，且登录态过期时需要人工重新扫码。

浏览器自动化已经支持至少 10 个隔离店铺，但平台页面改版、验证码和登录过期仍需要人工处理。
若后续获得官方客服 API 权限，可保留现有调度、状态和桌面界面，只替换每店的页面适配层。
