## 本次实际开发

### 拼多多：可启动的网页连接联调流程

1. 在“接入与试聊”创建并选择拼多多资料账户，启用本店商品与政策。
2. 展开“淘宝／拼多多连接联调”，点击“打开拼多多独立登录窗口”。每店使用单独浏览器目录，不复用飞鸽或日常浏览器资料。
3. 自行登录进入客服页，只保留一个该店客服标签。点击“检查已登录店铺”。工具通过当前页面同源请求核对店铺标识、店名和客服账号；不导出密码、Cookie 或登录令牌。
4. 核对显示身份，勾选确认并绑定。绑定不能悄悄改成别的店或别的客服账号；不同账号请创建新资料账户。
5. 在独立窗口刷新一次客服页，让工具观察该页面的消息通道。接收测试消息后点击“同步观察到的消息”。本版为人工触发同步，不宣称后台连续自动接待。
6. 下方选择采集的会话，查看原文并生成草稿。草稿沿用本店知识、双方上下文、售后分流和既有纠错回归能力。售后只暂停本地自动行为，实际转接仍须在原平台处理。
7. 首次只用指定的测试买家。核对顾客、完整草稿和资料后勾选确认，点击“审核并发送本轮拼多多草稿”。只尝试一次；只有匹配平台返回的消息标识、顾客和正文的客服回显，才记为已发送。HTTP 成功、输入框清空或相同文本都不够。

真实平台可能返回不同协议、二进制消息或新的字段，本版会停止并提示核对，不会用模型猜报文。未知、图片和卡片咨询尚未完成解析；它们使对应会话暂停，需要在原平台核对。此限制必须在真实联调中逐项补齐，不能按本版宣称全类型接待。

采集会保留平台消息 ID，重复事件不新增；同内容新消息仍会取消旧草稿。店铺身份变化、断线、缓冲溢出、未知结构、时间倒序、人工回复、撤回和转接均有保守处理。发生发送超时会持久化未知结果并阻止重发；不能通过恢复本地草稿绕过发送账本。当前未知发送需在原平台处理，该会话不继续试发。

### 淘宝：千牛只读兼容检查

选择淘宝资料账户，点击“只读检查千牛客户端”。检查限定在 AliWorkbench 进程的非登录窗口，最多读取800个控件与12层结构，不读取密码控件，不点击、不发送，也不改客户端文件。检查结果仅留在本机工作台。

检测到窗口或文字不代表已经识别店铺、买家、消息角色和稳定消息标识。本次未检测到正在运行的千牛窗口。仍需要用户登录后核对实际客户端结构，再实现该版本的可靠会话映射、发送与确认。没有这些证据，不开放淘宝自动接待。

## 与持续学习的关系

试接入采集的原文有独立来源和店铺范围。生成草稿进入既有纠错与知识候选流程，但不会被当作已发送、自动解决或真实成交样本。发送账本独立记录回显确认；本版没有将人工审核发送冒充自动接待实验。

后续验收需要分别验证：商品和政策更新能否改变实际答复；商家纠错能否通过评测发布；真实订单结果能否按店、会话正确关联。未经核实的聊天、特殊承诺和优惠不能自动改写经营政策。

## 真实店铺还需完成的验收

淘宝：登录后结构检查 → 确认稳定身份和角色 → 只读采集 → 草稿核对 → 指定测试买家发送与回显 → 人工接管 → 断线重连及后台长时间运行。

拼多多：真实身份接口和网页消息协议 → 文字及卡片/图片/撤回/系统事件 → 发送回显字段 → 账号切换与重连补齐 → 商品/订单/物流数据 → 单店小范围自动接待。每项记录实际证据，通过后才提升平台能力状态。

当前 `runtime_available` 对淘宝和拼多多仍为 False，主窗口“全部启动”、CLI 与原飞鸽适配器都不能把它们当作已验收的自动接待平台。拼多多试接入单独放在工作台，不影响飞鸽运行。

## 本地数据与发行

新增 `live_accounts`、`live_message_meta`、`live_deliveries` 表保存在已有 `data/reception/multichannel.sqlite3`，不会覆盖知识或旧会话。独立拼多多浏览器资料放在 `data/profiles/pinduoduo/<店铺标识>`。发行包保持空店铺，不包含登录资料、聊天、调试数据或密钥。
